# Рекомендации по VPS/VDS

Telegram не публикует универсальные минимальные требования к CPU, RAM и диску
для `telegram-bot-api`. Значения ниже — инженерная стартовая оценка для
текущей архитектуры TolaAI, больших файлов до 2 GB и указанного числа
параллельных отправок. После запуска её нужно уточнить по фактическим метрикам.

## Короткая рекомендация

Для текущего TolaAI без локальных AI-моделей оптимальная стартовая
конфигурация одного production-сервера:

| Ресурс | Рекомендуется |
| --- | --- |
| CPU | 8 vCPU с гарантированной долей процессора |
| RAM | 16 GB |
| Диск | 200 GB NVMe SSD |
| Сеть | порт 1 Gbit/s, трафик от 10 TB/месяц или без жёсткого лимита |
| ОС | Ubuntu 24.04 LTS x86_64 |

Если вынести весь стек `tola-bot-tg-api` на отдельный VDS:

| Ресурс | Рекомендуется |
| --- | --- |
| CPU | 4 vCPU |
| RAM | 8 GB |
| Диск | 100–160 GB NVMe SSD |
| Сеть | порт 1 Gbit/s, трафик от 10 TB/месяц |
| Связь с TolaAI | приватная сеть/VPC или WireGuard |

Под стеком `tola-bot-tg-api` здесь понимаются четыре контейнера, которые нужно
держать рядом: Python API, Python worker, Redis и официальный
`telegram-bot-api`. Worker и Bot API используют общий volume для `file://`,
поэтому разносить их по разным машинам без общего файлового хранилища нельзя.

## Варианты размещения

### Вариант A — всё на одном сервере

На одном VDS работают TolaAI backend, Celery, PostgreSQL, основной Redis,
Nginx, delivery-сервис, его Redis и local Bot API.

| Нагрузка | CPU | RAM | NVMe | Когда подходит |
| --- | ---: | ---: | ---: | --- |
| Тест/малый production | 4 vCPU | 8 GB | 100 GB | До нескольких больших отправок в час, concurrency 1 |
| Рекомендуемый старт | 8 vCPU | 16 GB | 200 GB | Concurrency 2, нормальный запас для PostgreSQL и Docker |
| Повышенная нагрузка | 12–16 vCPU | 24–32 GB | 300–500 GB | Много параллельных генераций и отправок, concurrency 4–6 |

Минимальную конфигурацию 4/8/100 следует считать временной. На ней сборка
официального C++-образа, Celery, PostgreSQL и параллельные видеооперации могут
создавать заметные пики CPU/RAM.

### Вариант B — TolaAI и Bot API на разных серверах

Рекомендуется, если файлы большие, отправок много или основной Mini App нельзя
замедлять Telegram-трафиком.

| Сервер | CPU | RAM | NVMe | Назначение |
| --- | ---: | ---: | ---: | --- |
| TolaAI | 6–8 vCPU | 12–16 GB | 120–200 GB | Backend, Celery, PostgreSQL, Redis, Nginx |
| Telegram delivery | 4 vCPU | 8 GB | 100–160 GB | API, worker, Redis, local Bot API |

Для 4 и более одновременных файлов размером около 2 GB сервер доставки лучше
увеличить до 8 vCPU, 16 GB RAM и 250 GB NVMe.

## Как считать диск

Главный потребитель диска — временные файлы отправок, а не Python-приложение.
Безопасная оценка:

```text
временный диск = concurrency × максимальный файл × 2.5
общий диск = временный диск + данные Bot API + Docker + логи + запас 30–50%
```

Примеры:

| Concurrency | Максимальный файл | Только рабочий запас | Практический размер VDS |
| ---: | ---: | ---: | ---: |
| 1 | 2 GB | 5 GB | от 60 GB |
| 2 | 2 GB | 10 GB | от 100 GB |
| 4 | 2 GB | 20 GB | от 160–250 GB |
| 6 | 2 GB | 30 GB | от 250 GB |

Коэффициент 2.5 учитывает исходный временный файл, операции Telegram, возможные
повторные отправки и незавершённые файлы после аварии. Настройте мониторинг с
предупреждением при 70% и критическим событием при 85% заполнения диска.

## Почему сеть важнее CPU

Один файл 2 GB сначала скачивается с S3 на delivery-сервер, затем отправляется
с сервера в Telegram. Это примерно 2 GB входящего и 2 GB исходящего трафика.

- На порту 100 Mbit/s один этап в идеальных условиях занимает около 160 секунд.
- На порту 1 Gbit/s — около 16 секунд, но реальное время будет больше.
- При concurrency 2–4 канал делится между заданиями.

Поэтому для production нужен именно гигабитный порт и понятная политика
провайдера по исходящему трафику. Для 1 000 отправок по 1 GB потребуется
примерно 1 TB исходящего трафика только в Telegram и около 1 TB входящего из
S3.

## Настройки под рекомендованный сервер

Для отдельного VDS 4 vCPU / 8 GB / 100–160 GB:

```env
DELIVERY_WORKER_CONCURRENCY=2
DELIVERY_MAX_FILE_BYTES=2000000000
DELIVERY_MAX_ATTEMPTS=4
DELIVERY_JOB_TTL_SECONDS=604800
```

Для единого сервера также явно ограничьте Celery TolaAI:

```yaml
services:
  worker:
    command: >
      celery -A backend.tasks.celery_app.celery_app worker
      -Q generation -l info --concurrency=2
```

Без `--concurrency` Celery обычно ориентируется на число доступных CPU и может
создать больше процессов, чем нужно для задач, которые в основном ждут внешний
AI API.

## Диски и резервное копирование

- Использовать NVMe SSD, не сетевой HDD.
- PostgreSQL TolaAI резервировать ежедневно и проверять восстановление.
- Сохранять Redis AOF delivery-сервиса и каталог данных local Bot API перед
  миграцией между серверами.
- Временный `delivery-files` не резервировать: это расходный volume.
- Настроить ротацию Docker-логов (`max-size` и `max-file`).
- Не хранить исходные генерации только на локальном диске — источником должен
  оставаться S3.

## Что измерить через две недели после запуска

- p95 времени скачивания из S3 и отправки в Telegram;
- максимальную глубину и возраст очереди;
- максимальное одновременное использование `delivery-files`;
- RAM каждого контейнера и PostgreSQL;
- месячный входящий/исходящий трафик;
- долю retry/failed и Telegram `429`.

После этих измерений concurrency можно повышать по одному. Увеличивать CPU без
проверки сети и диска обычно бессмысленно.
